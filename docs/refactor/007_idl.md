# 007 IDL 与服务实现规范

## 1. IDL 边界

每个服务维护自己的 IDL，并区分三类接口：

- `Public API`：经 Edge 暴露给 Web 或 CLI。
- `Internal API`：仅允许已认证的内部服务调用。
- `Event`：跨服务集成事实，不包含内部数据库结构。

建议的首批服务定义：

| 服务 | IDL Service |
|---|---|
| `media_auth` | `AuthService`、`TokenService`、`AuthInternalService` |
| `media_control` | `WorkspaceService`、`AgentConfigService`、`ScheduleService`、`TeamworkService`、`ControlInternalService` |
| `media_agent_gateway` | `SessionService`、`AgentTaskService`、`PlatformMCPService`、`AgentGatewayInternalService` |
| `media_plugin` | `PluginCatalogService`、`MCPConnectionService`、`PluginInternalService` |
| `media_storage` | `StorageService`、`StorageInternalService` |
| `media_notification` | `NotificationService`、`NotificationInternalService` |

`AgentGatewayInternalService` 必须提供 `ResolveSessionContext`，供平台内 MCP 使用 Session Token 解析用户、Workspace 和 Session。

## 2. 消息设计

- 字段名使用 `snake_case`，ID 使用字符串并声明语义。
- 请求必须显式携带资源定位和幂等键；分页使用统一游标模型。
- 内部委托身份使用公共 `DelegatedPrincipal`，调用方服务身份不从消息字段读取。
- API 错误使用稳定错误码，不把数据库错误直接暴露给调用方。
- 事件使用过去式命名，包含 `event_id`、`occurred_at`、聚合 ID 和版本。

## 3. 实现分层

所有接口实现严格遵守 `harness/contributing/architecture.md`：

```text
IDL / generated model
        ↓
transport handler
        ↓
application command or query
        ↓
domain service / aggregate
        ↓
repository and external adapters
```

- Handler 只做协议转换、认证上下文接入和错误映射。
- 领域层不依赖 Kitex/Hertz、数据库驱动、River 或具体消息系统。
- 数据库事务由应用层 `TxRunner` 控制；需要发布事件时同时写 Outbox。
- 生成文件只由生成器更新，禁止手工修改。
- Public 与 Internal 方法必须配置正确的路由/协议注解，并通过架构检查。

## 4. 变更顺序

先定义领域命令和不变量，再定义 IDL；生成代码后实现 Handler 与应用服务。禁止以旧 `control-plane` 路由结构直接反推新服务内部模型。
